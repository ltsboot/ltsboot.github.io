WHY LTSBOOT

When a line goes out of support, you have three options.

OPTION A

Jump to the next major now

  • New Java baseline, removed APIs, library upgrades
  • Regression testing across every service
  • Right, eventually. Rarely quick.

OPTION B

Stay put, unpatched

  • No work today
  • Every new advisory for your line stays open
  • Scanners and auditors keep flagging it

OPTION C

Stay put, patched

  • One BOM import, no code changes
  • Security and critical fixes on the Java versions your line supports
  • Time to plan the upgrade properly

GET STARTED

Drop it in. Build as usual.

The BOM pins the patched Spring artifacts and the fixed third-party versions. Gradle builds use the substitution plugin, which swaps the originals for the patched ones.

01Pick your line and add the BOM or the plugin
02Run your tests: nothing else changes
03Bump the fourth number for each patch release
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.github.ltsboot</groupId>
      <artifactId>lts-dependencies</artifactId>
      <version>2.7.18.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
plugins {
    id 'org.springframework.boot' version '2.7.18'
    id 'io.github.ltsboot.substitution' version '<latest>'
}

ltsboot {
    version = '2.7.18.1'
}

HOW A FIX SHIPS

Six gates between an advisory and your build.

Nothing reaches a release without a test that proves the hole and a person who signs off on the fix.

  1. 1 · Advisory Tracked daily GitHub, OSV and NVD feeds for every managed dependency.
  2. 2 · Triage Does it apply? Bump, backport, mitigation or not applicable, with the reason written down.
  3. 3 · Failing test Prove the hole first A regression test that fails on the unpatched code.
  4. 4 · Backport From public fixes only Ported to the line’s Java baseline; the full module suite must stay green.
  5. 5 · Review Independent and human Root cause, attack vector and API compatibility, then maintainer approval.
  6. 6 · Release Signed, on Maven Central Every changed file listed in the changelog with its CVE.
CRITICAL7 days after a public fix · 14 for our own HIGH30 days MEDIUMnext release, about 90 days LOWbest effort

Response targets, not guarantees. Fixes and critical bugs only, never new features.

Questions

Is ltsboot part of Spring or Broadcom?

No. It is an independent open source project. It uses only public open source code and is not affiliated with, endorsed by or sponsored by Broadcom Inc. or VMware.

Do I have to change my code or imports?

No. Package names and APIs are unchanged. You change build coordinates only, through the BOM or the Gradle plugin.

Which Java versions are supported?

The same as the original line. Boot 2.7: Java 8 and up, tested on 8, 11 and 17. Boot 3.5: Java 17 and up.

Which lines will you support next?

Lines whose open source support has ended and that are still widely used in production. Boot 3.5 is next.

Is it a replacement for upgrading?

No. It buys you time to plan the upgrade while staying patched.

How much does it cost?

Nothing. Everything is Apache-2.0 and published on Maven Central.
